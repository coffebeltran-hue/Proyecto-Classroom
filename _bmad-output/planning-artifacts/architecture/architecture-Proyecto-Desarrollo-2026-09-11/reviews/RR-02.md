## Roles and ownership

Names receive a unique `rr02_<run>_` prefix. All new roles lack SUPERUSER, CREATEDB, CREATEROLE, REPLICATION and BYPASSRLS. Separate API/worker logins are justified by queue access, not hypothetical tenant isolation.

| Principal | Actual authority |
| --- | --- |
| Existing local bootstrap administrator | Creates only isolated databases/roles; credentials remain outside Git. Not an application runtime identity. |
| `owner`, NOLOGIN | Owns disposable database, `rr02_proof` objects and `drizzle` journal. |
| `migration`, LOGIN/NOINHERIT | May explicitly SET ROLE to `owner`; serialized migration execution only. |
| `qowner`, NOLOGIN | Owns pg-boss schema/objects; database CREATE revoked after construction. |
| `maintenance`, LOGIN/NOINHERIT | May SET ROLE to `qowner`; precreates queues, supervises expiration/stats and rebuilds indexes. |
| `api`, LOGIN | CONNECT; USAGE on proof schema; SELECT/INSERT/UPDATE/DELETE on its marker. No pg-boss access. |
| `worker`, LOGIN | Same proof DML; USAGE on pg-boss; SELECT on `version,queue`; DML on `job,job_common`; EXECUTE on `job_now()`. No other queue grants or blanket future-object grants. |

Runtime roles own no objects and have no owner memberships, database CREATE/TEMP or schema CREATE. PUBLIC database/schema privileges are revoked in the disposable databases; search_path is `pg_catalog`, with qualified application references. Both owners revoke global default PUBLIC function EXECUTE. Proof-table DML defaults are confined to `rr02_proof`; future academic permissions require their own design. All installed pg-boss functions were confirmed security-invoker. No extensions or RLS were enabled.

Negative checks reject runtime CREATE/ALTER/DROP, role/database creation and owner SET ROLE; API queue reads and worker version writes, queue creation, administrative function calls and index rebuilds also fail. These credentials are trusted service boundaries, **not** per-tenant/queue isolation: worker job DML is intentionally powerful. Proposed AD-12 remains separate.

## Migration and deployment contract

**VERIFIED:** `packages/database/rr02/schema.ts` → `drizzle-kit generate` → reviewed, checked-in SQL/journal → pinned Drizzle Node migrator. Only a two-column infrastructure marker is created. The Node migrator is used instead of the CLI migrate command to provide explicit connection ownership, advisory serialization and sanitized failure handling; it uses the installed migration engine. First apply, unchanged replay and an injected failed second migration pass. Failed transactional SQL leaves neither its partial table nor a new applied-journal row. Journal containers may exist outside that transaction. Drizzle does not independently reject historical migration hash drift; evidence records the reviewed hash.

**DESIGNED BUT NOT EXECUTED as a release pipeline:** compare immutable migration artifacts against approved hashes; serialize releases; run migrations under migration credentials before dependent API/worker versions. Never run push, startup migrations or invented automatic down migrations. Use additive expand/contract changes while old code runs; remove old fields only after old consumers stop. Roll back code only when compatible with the resulting forward schema; otherwise forward-repair or explicitly restore. Future application-schema readiness checks must be defined with that schema. The current idle bootstrap has no academic schema/readiness claim.

pg-boss manages its own construction/versioned migration SQL, separately from Drizzle. Owner construction and exact-schema runtime rejection were executed. **A real previous-version upgrade was not executed**: changing the test version number to 41 proves fail-closed startup, not an upgrade. Before upgrading pg-boss, inspect its actual upgrade SQL/async work, quiesce incompatible consumers, apply under queue authority, recheck grants, and prove restoration/compatible restart. No mixed-version rolling compatibility is claimed.

## Queue, failures and restore

**VERIFIED:** restricted startup forcibly disables migrate/supervise/schedule. Precreated queues enqueue, process and complete; one deliberate failure retries successfully. Ordinary duplicate sends produce distinct jobs; a configured singleton suppresses its duplicate only within that primitive's scope. Graceful stop and restart pass. A forcibly terminated child leaves an active job; owner supervision expires it and the worker redelivers/completes it. A timed-out synthetic handler retries. Owner maintenance and 11 index rebuilds succeed; worker rebuild fails. Maintenance needs explicit execution with separate credentials; this does not select a new service or hosting scheduler.

Callbacks explicitly use `transactional:false`; the blocked child connection was observed idle with no transaction. No provider was called. Future code must commit durable intent before network I/O, then record results separately; this fixture cannot prevent arbitrary future code from opening another transaction. AD-13 inbox/outbox and business idempotency remain proposed/unimplemented. Queue timeout cannot cancel arbitrary effects or guarantee exactly-once behavior.

Missing schema, mismatched schema, wrong password and a refused local endpoint fail safely without installation. Raw errors are replaced by fixed diagnostics, failed connections close, and credential-bearing mock errors are tested. This is not a running-server outage/reconnect or host-power-loss experiment.

**VERIFIED:** custom-format pg_dump → separate empty database → pg_restore preserved two marker rows, one migration row, eight queue rows, owners/ACLs/default ACLs. A restored queued job completed. Roles already existed in the same cluster. Existing `classroom_dev` was not altered. Disposable databases, dump files and failed-run evidence remain under `.local/rr02`; there is no automatic destructive cleanup.
